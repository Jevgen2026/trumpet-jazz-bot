# ТЗ: PoC «Интонация трубы» — анализ чистоты игры

Версия 0.1 · проект @JazzTrumpetLibraryBot · автор Хрустицкий Игнат, 10-В

## 1. Цель и границы

**Цель.** Дать ученику-трубачу обратную связь по **чистоте интонации**: он записывает голосовым сообщением, как играет ноту (или гамму), бот определяет высоту звука и говорит — в строе он или фальшит, на сколько центов высит/низит, и даёт совет.

**Почему именно это (а не «находит неправильные ноты»).** Труба монофонична и имеет непрерывную высоту тона (амбушюр) — на ней реально «фальшивить», и это измеримо в центах. Для «не та нота» нужен машиночитаемый эталон (MIDI/MusicXML), которого у нас нет (только PDF). Поэтому PoC — про интонацию, без сверки с нотами. Это «изюм» для защиты и фундамент будущего AI-тренажёра.

**В scope:**
- Один инструмент — труба (B♭).
- Только монофония (одна нота в момент времени).
- Асинхронно: голосовое → анализ → отчёт. Без реального времени.
- Режим A (ядро): одна длинная нота — тюнер + стабильность.
- Режим B (растяжка): простая гамма/упражнение — поноточный разбор.

**Вне scope (явно):**
- Полифония, аккорды (это гитара/ф-но — другой класс задач).
- Сверка с нотным текстом / «неправильная нота».
- Реальное время / live-коучинг.
- Ритм/темп (для этого уже есть метроном — отдельная фича).
- Другие инструменты — НО архитектура не хардкодит B♭: строй и транспозиция выносятся в параметры (см. §6), чтобы потом добавить тромбон/сакс/кларнет/контрабас без переписывания.

## 2. Пользовательский сценарий

1. В меню бота — кнопка **«🎤 Проверить интонацию (бета)»**.
2. Бот: «Запиши голосовое: в тихой комнате, поднеси телефон ближе. Сыграй ОДНУ ноту ровно 3–5 секунд. Перед этим можешь настроиться по тюнеру.»
3. Пользователь шлёт голосовое.
4. Бот за ~5–10 сек отвечает отчётом (текст; в идеале + картинка-график «центы во времени»).
5. Согласие/приватность: одной строкой «аудио используется только для анализа и не сохраняется».

## 3. Что считаем (музыкальная логика)

- **Эталон строя:** A4 = 440 Гц (параметр, по умолчанию 440).
- **Отклонение в центах** от ближайшей равномерно-темперированной ноты:
  `cents = 1200 * log2(f0 / f_nearest)`, где `f_nearest` — частота ближайшей ноты.
  Отклонение в центах **не зависит от транспозиции** (одинаково, как ни называй ноту).
- **Название ноты.** По умолчанию показываем **концертную** высоту (реальный звук), и подсказываем написанную для трубы (на тон выше): напр. звучит A4 → для трубы пишется B4.
- **Обрезка атаки/затухания:** первые/последние ~15% сигнала отбрасываем (на атаке высота нестабильна), анализируем устойчивую середину.
- **Метрики:** медиана отклонения (центы), разброс (стандартное отклонение = «дрожание»), длительность устойчивого звука.

**Музыкальные допуски (вердикт):**
| |cents| | Вердикт |
|---|---|---|
| ≤ 5 | ✅ в строе (отлично) |
| 5–15 | 🟡 чуть высит/низит |
| 15–30 | 🟠 заметно высит/низит |
| > 30 | 🔴 сильно мимо (или не та нота) |

Разброс > 20 центов → совет про опору/стабильность звука.

## 4. Технический пайплайн

1. **Приём.** Telegram voice = OGG/Opus, 48 кГц моно.
2. **Декод в PCM:** через `ffmpeg` (OGG→WAV 44.1/48 кГц mono float). Проверить наличие ffmpeg на сервере, при отсутствии — `apt install ffmpeg`.
3. **Определение высоты (f0 по кадрам):** `librosa.pyin` (монофонический трекер, CPU, без GPU). Возвращает f0(t) + voiced-флаги. Альтернатива на будущее — CREPE (точнее, но тяжелее/GPU).
4. **Постобработка:** оставить только voiced-кадры, обрезать края, посчитать центы по §3.
5. **Вердикт + совет** по таблице §4 (текст генерится по правилам; позже — через Claude для «человеческого» тона).
6. **(Растяжка) График:** `matplotlib` → PNG «отклонение в центах во времени», отправить как фото.
7. **Очистка:** временные файлы удалить сразу после анализа; аудио не хранить.

**Сигнатуры (ориентир):**

## 5. Интеграция в бот

- Кнопка в главном меню + команда `/intonation`.
- Состояние `awaiting_intonation` (как `awaiting_metro_bpm`).
- Хендлер `MessageHandler(filters.VOICE, handle_voice)` → если ждём интонацию: скачать файл → ffmpeg → `analyze_intonation` → ответ.
- Тяжёлый анализ не блокирует event loop: вынести в `run_in_executor` (ThreadPool).
- Зависимости (в `requirements.txt` отдельной группой): `numpy`, `librosa`, `soundfile`, `matplotlib` (для графика). ffmpeg — системный.

## 6. Расширяемость (на другие инструменты)

- `a4` и **транспозиция/строй — параметры инструмента**, не константы.
- Таблица строёв (из скилла music-expert): труба/кларнет/тенор-сакс B♭, альт/бари-сакс E♭, тромбон/контрабас — C (контрабас звучит на октаву ниже).
- Поноточный разбор гаммы (режим B) — общий для всех монофонных.
- Полифонию (гитара/ф-но) НЕ трогаем в этой ветке — другой движок (multi-pitch).

## 7. Критерии приёмки (для защиты)

1. Чистая длинная нота трубы 3–5 c → бот возвращает название ноты + центы, **совпадение с эталонным тюнером в пределах ±5 центов**.
2. Тишина/шум/слишком коротко → понятное сообщение «не услышал устойчивой ноты, попробуй ещё», без падения.
3. Круг «записал → ответ» < ~10 секунд.
4. Работает в практическом диапазоне трубы (концертно ≈ E3–C6).
5. Аудио не сохраняется после анализа.

## 8. План реализации (фазы)

- **Ф1 (ядро PoC):** одна длинная нота → центы + вердикт (текст). ← минимум для защиты.
- **Ф2:** график «центы во времени» картинкой.
- **Ф3:** режим гаммы — поноточный разбор.
- **Ф4 (крупная, см. §9b):** оценка пьесы целиком с указанием такта — ТРЕБУЕТ MusicXML/MIDI-эталона. Сначала на 1–3 монофонных пьесах.
- **Ф5:** обобщение на тромбон/сакс/кларнет/контрабас (через таблицу строёв).
- **Ф6 (продукт):** «человеческие» советы через Claude, трекинг прогресса, монетизация СЕРВИСА (не нот) через Stars.

## 9b. Расширение: оценка произведения ЦЕЛИКОМ с указанием такта

Цель пользователя: залить запись всей пьесы → бот оценивает всё произведение и **указывает номер такта и саму ошибку**. Это отдельная, более крупная фича, чем интонационный PoC.

**ГЛАВНОЕ УСЛОВИЕ — машиночитаемый эталон.** Чтобы сказать «в такте N ошибка», нужен эталон пьесы в **MusicXML или MIDI** (ноты + длительности + разбивка по тактам). PDF не годится (картинка). Без эталона фича невозможна.

**Источники эталона (по убыванию удобства):**
1. Выгрузка MusicXML/MIDI (часто умеет MuseScore/расширение — проверить!).
2. OMR (Audiveris, open-source) PDF→MusicXML + ручная корректура.
3. Ручной набор в нотном редакторе (медленно, но надёжно для 1–3 демо-пьес).

**Движок сравнения:**
1. Эталон: MusicXML → ноты с номерами тактов и ожидаемыми высотами/длительностями.
2. Исполнение: голосовое → монофонная транскрипция (онсеты + высоты; pyin + onset detection).
3. Выравнивание performance↔score через **DTW** → привязка каждой сыгранной ноты к такту.
4. Классификация ошибок: не та нота / пропуск / лишняя нота / тайминг (рано-поздно) / интонация (центы).
5. Отчёт: список по тактам («такт 12: сыграно G, ожидалось A♭») + общий % точности.

**Границы:**
- Реально: монофонная труба + пьесы с готовым MusicXML-эталоном. Демо на 1–3 пьесах.
- Нереально коротко: «любая пьеса из всей библиотеки» (нужен эталон под каждую).
- Полифония (гитара/ф-но): research-grade, вне школьного срока.

**Зависит от:** наличия MusicXML/MIDI. Это блокер №1 — решить до реализации.

## 9c. Идея-перспектива: аудио → ноты мелодии + аккорды + минусовка + транспозиция

Сценарий: пользователь шлёт ПРОИЗВОЛЬНОЕ аудио → бот возвращает ноты основной мелодии + минусовку из этого же аудио; для ф-но/гитары — мелодия с аккордами над строкой; ноты подстроены под выбранный инструмент (труба B♭: написанное до звучит как концертное си♭).

Это НЕ одна фича, а цепочка ML-этапов разной надёжности:
| Часть | Инструмент | Реалистичность |
|---|---|---|
| Транспозиция под инструмент | арифметика полутонов (таблица строёв music-expert) | ✅ тривиально |
| Аудио → ноты мелодии | Basic Pitch / Klangio → MusicXML → рендер (LilyPond/MuseScore CLI) | ⚠️ лоссово, ручная правка; джаз слабо |
| Аккорды над мелодией | распознавание аккордов (chordino/madmom/autochord) | ⚠️ попса ок, джаз (альтерации) шатко |
| Минусовка из аудио юзера | разделение стемов (Demucs) | ⚠️ вокал убирает хорошо, инстр. мелодию плохо |

**Границы:** на произвольной записи (особенно джаз) — черновик, не издательское качество. Транспозицию берём сразу (уже в тюнере). Полноценная авто-нотация — фича-перспектива, демо на чистом монофонном входе. Из символьных нот (MIDI/MusicXML) всё это чисто; из аудио — лоссово (та же закономерность, что в §9b).

**Сверка точности транскрипции (self-check):** без эталона измеряется не «точность», а **уверенность/самосогласованность**. Метод: ре-синтез транскрипции в аудио → извлечь высоту/хрому → DTW-сравнение с оригиналом юзера → % совпадения; + по-нотные вероятности из Basic Pitch. Вывод честный: «уверенность ~85%, такты 5,12 под вопросом». Не писать «100% точно». Терминология: «уверенность», не «точность».

**Вкладка «🎤 Мои ноты» (пользовательские ноты):** сгенерённые по запросу ноты хранятся ОТДЕЛЬНО от публичной библиотеки, по `user_id` (PDF в `user_notes/<user_id>/`, метаданные в **SQLite** — рекоменд., т.к. персональные данные на многих юзеров; публичная библиотека остаётся в notes.json). Эти ноты в библиотеку НЕ попадают. Это решает конфликт с принципом качества и снижает копирайт-риск (личная генерация ≠ публикация). Поток: аудио → транскрипция+уверенность+минусовка → в «Мои ноты» юзера → (опц., позже) «предложить в библиотеку» → модерация Игнатом.

**Авто-пополнение ПУБЛИЧНОЙ библиотеки (если сгенерённой пьесы нет в боте):** НЕ авто-публиковать. Лоссовый черновик в публичной библиотеке убивает гл. принцип «проверенное качество, не лотерея MuseScore» + копирайт по конвейеру + спам/дубли. Правильно — ОЧЕРЕДЬ МОДЕРАЦИИ: бот делает черновик пользователю → по желанию отправка КУРАТОРУ (Игнату, `YOUR_USER_ID`) на проверку/правку/одобрение → только после этого запись в notes.json + notes/. Переиспользует существующий поток «📝 Предложить произведение». Определить «есть ли уже пьеса» из аудио надёжно нельзя без муз-распознавания (ACRCloud/AudD). Авто-добавление без ревью — только для контролируемого контента (PD, свои аранжировки).

## 9. Риски

- Декод Opus требует ffmpeg — проверить/поставить.
- Качество микрофона телефона + шум комнаты → советовать ближний микрофон, тишину.
- `librosa` тянет numpy/scipy (объём) — ставить в тот же venv; на CPU Hetzner анализ 5-сек клипа < 2 c.
- Шумные/слабые ноты → отбраковывать по voiced-порогу, просить переписать.
